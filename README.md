# DRF 公平共享算力调度器

面向中型 AI 公司共享算力池（64 核 / 256GB / 8 GPU）的多租户批处理调度器。
解决四个团队的异构作业（大训练 / 评测跑批 / 数据预处理）之间的资源争抢：
**CV 的大训练不再霸占整机，轻量评测不再饿死，上游失败下游立即取消，
调度器重启后在途作业可从 WAL 恢复，手抖重复提交不会把 GPU 占双份。**

唯一第三方源码依赖是 `golang.org/x/sync/errgroup`（已 vendor 到 `vendor/`），
其余全部使用标准库：`container/heap`、`sync`、`context`、`encoding/json`、
`os/signal`。DRF 算法、熔断器、WAL 均为自研，存储为内存 + 追加日志，
**不引入数据库或任何中间件进程**。

## 快速开始

```bash
go run . demo      # 内置演示：依赖组 / 幂等 / 熔断 / 优雅停机 / WAL 重放（验证命令）
go run . status    # 四团队异构作业的调度轨迹与资源占用
go run . submit -wal w.wal -id j1 -tenant cv -kind train -jobcpu 32 -jobgpu 4
go run . drain     # 优雅停机排空与 WAL 落盘
go run . bench     # 性能基准
go test ./...      # 单元/集成测试（含 -race）
```

`submit` 子命令会在前台运行并捕获 `SIGTERM`/`SIGINT`，可直接 `kill -TERM <pid>`
验证优雅停机。

## 文件结构

| 文件 | 职责 |
|---|---|
| `scheduler.go` | DRF 分配器核心、优先队列、熔断器、幂等与依赖治理 |
| `pool.go` | 资源池：三维原子记账、按租户聚合、预留/释放 |
| `runner.go` | errgroup 执行器、取消传播、同键互斥、优雅停机排空 |
| `job.go` | 作业状态机、幂等键、重试计数 |
| `wal.go` | 追加式预写日志、批量 fsync、崩溃重放恢复 |
| `main.go` | 终端入口与子命令、SIGTERM 捕获、内置演示与基准 |

数据流：**提交 → 幂等去重 → WAL 追加 → DRF 优先队列 → errgroup 执行组
→ 资源池扣减 → 回写 WAL**。

## 四个痛点的落地方式

### 1. DRF 公平共享：轻量作业不再饿死

对每个租户计算 CPU/内存/GPU 三维占比，取其**最大值**为主导份额
`dominant(t) = max(cpu占比, mem占比, gpu占比)`，调度时始终挑主导份额最低的租户。

- **不是简单的轮转**：纯轮转会浪费资源（GPU 型作业与内存型作业粒度不同）。
  DRF 让"资源画像互补"的租户自然错峰，用满整机的同时保证人人有份额。
- **冷启动补偿**：新租户用量为 0，主导份额必然最低，会立刻拿到资源 ——
  这正是 DRF 想要的短时公平（见 `TestColdStartNewTenantGetsShare`）。
- **边界处理**：
  - 请求为零 / 负数 → `Resources.Validate` 拦截；
  - 请求超额 → `TryReserve` 三维打包 CAS 整体拒绝，不会出现"占了一半"；
  - 主导份额并列 → 按 `(dominant, dCPU, dMem, dGPU, 提交序号)` 复合排序，
    全部并列时退化为 FIFO，保证先来者不被饿死；
  - 资源装不下 → 作业进入 `unfit` 暂存桶，资源释放后重新参与竞争，
    **不会丢失也不会永久阻塞队列**。

实测（`TestDRFDoesNotStarveLightTenant`）：hog 租户占住 8/10 核后，
主导份额已远高于 light，light 的 2 核作业立刻被调度上去。

### 2. errgroup 取消传播：上游失败，下游立即取消

一个依赖组 = 一个 `errgroup.Group` + 一个派生 `context`。组内任一作业返回
非 nil error → errgroup 取消组 context → 兄弟作业的 `ctx.Done()` 关闭 →
它们**排空在途计算**并 `return ctx.Err()`。

关键设计：

- **资源必然归还**：每个作业的执行体用 `defer lease.Release()` + `Complete()`
  收尾，无论成功/失败/取消/`panic`，资源都回到池里（`TestCanceledSiblingReleasesResources`、
  `TestPanicInTaskReleasesResources`）。租约释放是 CAS 幂等的，杜绝双退/漏退。
- **部分结果不泄漏**：被取消的作业不会产出结果，且立刻从待调度队列摘除。
- **级联取消可传递**：`root -> mid -> leaf` 三层依赖，上游失败逐级取消
  （`TestCascadeIsTransitive`），不会让下游挂在队列里空占。
- **组取消后不浪费重试**：作业进入重试时若所属组已被取消，直接落 `canceled`
  而不是白白消耗一次重试机会（组 context 已死，重试必然立刻被取消）。

### 3. 幂等、同键互斥与熔断

- **提交期幂等**：同幂等键只入队一次，重复提交返回**已有作业句柄**
  （`Submit` 返回 `created=false`），实测资源占用零变化。
- **执行期互斥**：per-key `sync.Mutex` 的 `TryLock`；拿不到锁说明同键正在跑，
  立即释放本次预留并返回 `ErrKeyBusy`。因此同键作业**只执行一次**，
  GPU 不会被双份占满（`TestIdempotencyBlocksDoubleGPUReservation`）。
- **指数退避重试**：最多 3 次，退避 `base * 2^(n-1)` 并叠加基于作业序号的
  **确定性抖动**，避免同租户多个失败作业同时重试形成尖峰
  （`TestRetryBackoffGrows`）。
- **熔断器**：按租户统计，**最终失败**连续达 5 次熔断 60 秒；
  冷却结束进入半开放，**只放一个探测作业**探活；探测失败立刻重新熔断并重新计时。
  - 熔断是**按租户**隔离的：一个坏租户不会影响其它团队
    （`TestCircuitBreakerOpensAndBlocks`）。
  - 中间重试**不计入**熔断：熔断衡量的是"作业最终失败"。若把重试也计入，
    一个重试后成功的作业会误伤整个租户（`TestRetryableFailureDoesNotTripBreaker`）。

### 4. 优雅停机与 WAL 恢复

`SIGTERM`/`SIGINT` → `GracefulStop`：

1. 置 `draining`，**立即**停止接收新提交（后续提交返回 `ErrDraining`）；
2. **关闭准入门**后等待在途作业排空，上限 30 秒；
3. 超时则强制取消残留任务（各作业收到 `ctx.Done()` 后自行排空）；
4. 最后一次性 `fsync` WAL 落盘，确保重启后能重放恢复。

WAL 是换行分隔的 JSON 事件流，**提交先落盘再入队**，保证崩溃不丢作业。
重放按事件语义幂等（同 ID 只认首条 submit，终态覆盖），因此重放两次结果一致。
尾部撕裂的半条记录（崩溃时只写了一半）会在**打开时**截断修复 —— 必须在任何
追加之前完成，否则新记录会被拼接到半条 JSON 后面，把两行粘成一条永远无法解析
的数据（`TestWALTruncatesTornTail`）。

`running` 状态的作业在崩溃后丢失了执行体，重启时按 `pending` 重排；
幂等键保证它不会与残留实例双跑。

## 并发正确性

调度器的关键路径由 `sync.Mutex` 保护，资源池用三维打包 CAS + 分片租户账本：

- **多维原子预留**：三维已用量按 `cpu 21 位 / mem 38 位 / gpu 5 位` 打包进一个
  `uint64`，用**单次 CAS** 完成"要么全成、要么全不成"，避免多维分步扣减导致
  的中间态（例：CPU 扣成功但内存扣失败）。上界 2M 核 / 256TiB / 31 GPU，
  远超 64 核 / 256GB / 8 GPU 的规模。
- **租户账本分片**：租户名哈希到 64 个分片锁，多租户并发扣减几乎不互相阻塞。

两处值得记录的坑（都已修复并有回归测试）：

- **`sync.WaitGroup` 的 Add/Wait 竞态**：优雅停机的 `inflight.Wait()` 可能与新作业
  的 `inflight.Add(1)` 并发，导致 Wait 提前返回、**误判已排空**。修法是加一道
  **准入门**（`admitMu`）：`Add(1)` 与关闭准入门严格串行，停机后不再接纳新作业。
- **Once 内写、外部读的竞态**：根 context 原先在 `sync.Once` 里创建，
  却在外层读取。加了数据竞争。修法是构造时一次性建好，之后只读。

`go test -race ./...` 全绿；`demo`/`status`/`drain`/`bench` 在 race 构建下均无竞争。

## 性能

`go run . bench` 实测（Apple Silicon，本地文件系统）：

| 指标 | 实测 | 目标 | 结论 |
|---|---|---|---|
| DRF 单次决策（1000 条待调度） | 平均 0.001ms / P99 0.003ms | < 1ms | **PASS**（余量约 300×） |
| 资源池扣减（64 线程竞争同一批租户） | 平均 4.5µs / P99 7.3µs | < 100µs | **PASS**（余量约 14×） |
| 100 并发作业端到端 | 0.5s / 约 180 作业/s | 支撑 100 并发 | **PASS** |
| 优雅停机排空 + 落盘 | 0.3s | < 30s | **PASS** |
| WAL 单次 `fsync` | 平均 4~8ms | < 5ms | **受限于磁盘，见下** |

### 关于 WAL fsync 未达标

这一条**没有达到题面的 < 5ms**，根因不在实现：

- 本机裸 `fsync`（不经过任何缓冲、只写 4KB 后同步）的地板延迟实测
  **平均 4.5ms、P99 6.8ms**。也就是说"单次 fsync < 5ms"这个目标本身
  就贴着本地存储的物理地板，超出部分由磁盘决定。
- 实现侧能控制的部分已经做到位：WAL 用 **20ms 批量合并 fsync**（`bufio` 64KB
  用户态缓冲 + 周期刷盘），把**每条事件摊销到约 300~500µs**，
  因此 WAL 不会成为吞吐瓶颈。基准里同时打印 `raw fsync`（存储地板）
  与 `批量 fsync 摊销`（实现可控）两个口径，避免用单次 fsync 指标
  误判调度器吞吐。

若部署在 NVMe 或使用 `O_DIRECT`/更大页对齐的写入，该指标会显著改善；
这是环境属性，不是代码缺陷。

## 已知取舍

- **WAL 只记录状态，不记录执行体**。作业的 `Run` 闭包无法序列化，重启恢复时
  按 `Job.Kind` 从 `taskRegistry` 重新水合。注册表里没有的 Kind 降级为 noop。
  真实系统里这一步应是"按作业镜像/代码版本重新拉起容器"。
- **熔断器状态不跨重启持久化**：重放时按重放出的失败作业重建内存状态，
  冷却窗口本身不恢复（重启等于给了所有租户一个新的冷却期）。
- **单实例内存态**：按题面要求不引入数据库/中间件，因此租户账本与队列
  只在本进程内；多副本部署需要额外的分布式选主，本实现未涉及。
