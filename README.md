# sigstore — 可嵌入的列存内核

零第三方依赖，仅用 JDK 21 标准库。解决运营商信令分析平台的四个具体问题：

| 现场症状 | 本内核的做法 |
|---|---|
| 行存多列过滤 40s+ | 倒排位图下推，等值/区间过滤与命中行数无关 |
| 后台页合并持写锁，堵死入库 3-8s | 无锁 MVCC 快照读：读路径不取任何锁 |
| OOM 重启后半截事务残留，地市双倍计数 | WAL fsync 作为唯一持久化屏障 + 按提交序号回放 |
| 同一 SQL 两次 Top10 顺序不同 | rowId 恒等提交序；聚合用 TreeMap；TopN 用全序比较器 |

## 架构

写入：`append` 暂存行 → `commit()` 在提交锁内分配 rowId、写时复制建页
→ 写 WAL → **fsync（唯一屏障）** → 装页版本 → 推水位线。

读取：`beginRead()` 抓快照号 S → 二分提交点表得到可见行数 → 位图求交集
→ 按 rowId 升序回读列向量。

关键不变量：**内存可见性永远不领先于 WAL 的持久化边界**。fsync 之前不装页，
所以崩溃时不存在"内存里有、盘上没有"的行——这正是双倍计数事故的根因。

### 文件

- `ColumnStore` 列族/页分配/页缓存；`Page` 页编解码
- `BitmapIndex` 倒排位图 + 区间分段位图
- `SnapshotManager` 快照注册；`CommitPoints` 提交点表
- `WALJournal` 预写日志；`RecoveryEngine` 恢复；`CrashInjector` 崩溃注入
- `WriteTransaction` 写事务；`BulkLoad` 批量装载；`QueryEngine` 查询与聚合
- `Schema`/`Row`/`Filter` 类型定义

## 实现中踩到的坑

这些都是实测暴露、且都有测试固定的：

1. **`ByteBuffer.flip()` 陷阱**。用绝对定位 `putLong(pos, v)` 写完记录后 position 仍是 0，
   此时 `flip()` 把 limit 置 0，`remaining()` 为 0 —— 一条字节都写不出去，WAL 全程静默为空。
2. **页尺寸放大 28 倍**。6 列 ×64 行只需 2304 字节负载，却按 64KB 分页。
   200 万行要 11.7GB 常驻内存，直接缓冲根本放不下。改为按负载对齐分页后降到约 72MB。
3. **每行都复制整页**。写时复制基线取错对象——同一事务内应取"本事务已暂存的那一版"，
   否则前一行会被后一行覆盖（症状：只剩最后一行）。
4. **复用暂存页时忘了推行数**。页头停留在首次追加时的值，`rowCount` 恒为 1，扫描只认一行。
5. **`BitSet.set(from,to)` 右端开区间**。传入半开区间时多减了 1，区间过滤结果恒为空。
6. **下推失败却没有回退求值**。某列没建位图时 `pushdown` 返回 null，但扫描只用位图当掩码、
   从不重新判断谓词 —— 按高基数列过滤会**静默返回全表**。
7. **pageSize 编码压成 2 字节**。65536 回绕成 0，恢复侧校验把整条记录判为尺寸不符而丢弃。
8. **并发写事务的 rowId 重叠**。rowId 若在 `beginWrite` 时分配，两个事务会各自认为拥有
   同一段行号，位图错位、页内容互相覆盖。改为提交锁内分配。
9. **默认构造的 `CrashInjector` 会崩**。`new CrashInjector()` 是生产默认参数，
   原本会武装 AFTER_SYNC，等于线上随时凭空崩一次。改成不传 stage 即惰性。

## 测试有效性

写了 8 个人工变异（把 AND 改成 OR、区间漏下界、段边界差一、恢复重放未提交事务、
去掉 WAL CRC 校验、装页早于 fsync 等）逐个验证是否被测试抓住。

**已抓住**：AND 改 OR、区间漏下界、段边界差一、IN 改交集、EQ 返回全量位图、
装页早于 fsync、重放未提交事务、去掉 CRC 校验。

两处未被抓住，原因是它们在正常 WAL 下确实不可达，而非测试缺失：
- 去掉恢复时的 `version` 比较 —— 回放严格按 LSN 升序且 version 同源单调，顺序已保证正确；
  该判断实为应对"日志被外部损坏/重排"的防御，已在代码注释中说明其真实作用。
- 无条件接受数据文件页 —— 同理，数据文件先载入、WAL 后覆盖，方向本就正确。

对不可达逻辑没有强行造测试，而是把结论写进注释。
M7/M9 一开始能存活，是因为用例构造得不够狠（8 字节太短、走不到 CRC 分支；
恢复后 WAL 是空的、根本没触发重放），补强用例后才抓住。
