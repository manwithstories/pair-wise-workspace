# aisched — DRF 公平共享的共享算力池调度器

一台共享算力池（64 核 / 256GB 内存 / 8 张 GPU），四个算法团队提交异构批处理作业。
调度器解决四件事：**公平**（不让大作业独占）、**协作**（上游失败要取消下游）、
**可靠**（崩溃后在途作业自动恢复）、**幂等**（重复提交不会双占 GPU）。

```
go run . demo     # 跑内置示例：依赖组、重复提交、熔断、优雅停机、WAL 重放恢复
go run . bench    # 性能自检（对齐需求里的硬指标）
go test ./...     # 单元 + 端到端测试
```

## 架构

核心 5 个文件（`vendor/` 只放 `golang.org/x/sync/errgroup`，其余全标准库）：

| 文件 | 职责 |
|---|---|
| `scheduler.go` | DRF 分配器：主导份额打分、优先队列、同键互斥、熔断器 |
| `pool.go` | 资源池：原子计数 + 按租户聚合的扣减/归还账本 |
| `runner.go` | errgroup 执行器：作业组 fan-out、取消传播、退避重试、排空 |
| `job.go` | 作业状态机 `pending→running→succeeded/failed`、幂等键、资源三维 |
| `wal.go` | 追加式预写日志：帧校验、组提交、崩溃重放 |
| `main.go` | 终端入口：主循环、`submit/serve/drain/status/demo/bench`、信号处理 |

数据流严格按需求：

```
提交 → 去重 → WAL 追加 → DRF 优先队列 → errgroup 执行组 → 资源池扣减 → 回写 WAL
```

## 几个关键设计决定

**DRF 打分用 `max(t, t')`。** 教科书 DRF 只看「放入作业后的主导份额 `t'`」，
于是一个空闲租户即使 `t'` 已经超过所有竞争者，只要它仍是全场最小就会被立刻放行——
CV 团队那个「一占半天」的 8 卡训练正是这样反复插到评测前面。这里改用
`max(t, t')`，相当于加了一条「份额不能突然暴涨」的软约束：抢跑会让分数超过
竞争对手，从而被推迟到真正需要它的时候。

**零请求维度不参与份额取最大。** 一个只要 2 核内存的轻量评测，不应该因为 GPU
维度是 0 而被算成 0 份额。零需求维度对份额没有约束力。

**Plan / Acquire 两步决策。** 早期版本一边持调度器锁一边扣资源，而运行中作业的
释放路径是「先查调度器拿租户、再锁资源池」——两个方向构成 AB-BA 死锁，表现为
dispatch 之后进程挂死。现在把决策与扣减拆开，并让释放路径完全不碰调度器
（租户信息固化在 `Job.ReleaseHold` 上），彻底消除锁序反转。

**同键互斥放在执行期，而不是只放在提交时。** 幂等提交只在入队去重一次，
之后作业可能被重投、也可能被 WAL 恢复出第二份；`keyedMutex` 才是防双跑的闸门。
资源池侧还维护一份「当前持有」账本，同一个键同时扣两次会被直接拒绝——
这是「手抖重复提交 → GPU 被双份占满」的最后一道防线。

**熔断取消不计入连续失败。** 上游取消不是租户的错，不该推进熔断计数，
否则一次依赖失败就能把无辜的租户打到熔断。

**重放只恢复「在途」作业。** 已经 `completed` 的作业绝不复活——否则每次重启
都会把跑完的训练/评测再烧一遍卡。它们的终态只保留在记忆表里，供下游依赖判定使用。

## 验证

`go run . demo` 覆盖九个场景：DRF 公平性、幂等提交、依赖组取消传播（含成功对照组）、
指数退避重试、熔断与半开放探活、优雅停机（真实 SIGTERM）、WAL 重放恢复。
停机走的是 `syscall.Kill(getpid(), SIGTERM)`，与现网完全相同的信号路径。

`go run . bench` 实测（预算来自需求）：

| 指标 | 实测 | 预算 |
|---|---|---|
| DRF 单次决策（1000 待调度） | ~1.4µs | 1ms |
| 资源池扣减（8 goroutine 竞争） | ~660ns | 100µs |
| WAL 单次 fsync | ~4.2ms | 5ms |
| 100 并发作业端到端 | ~7ms | 20s |
| 优雅停机排空 + 落盘 | ~97ms | 30s |
