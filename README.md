# 市级自然资源测绘平台 — 空间检索服务

后端空间检索服务：为数千万级地理要素（POI、地块覆盖区、管线节点）提供 **近邻查找** 与 **范围圈选**，
用于应急选址与资源调度。

Java 17 LTS · JUnit Jupiter 5.10.2 · jqwik 1.8.5 · 零第三方运行时依赖（仅标准库）。

## 快速开始

```bash
./mvnw -q test                                  # 94 项测试（JUnit 5 + jqwik 属性测试）
./mvnw -q test -Dtest=KDTreeIndexTest           # 单个测试类
java -Xmx512m -cp target/classes com.citygis.spatial.demo.DispatchConsole
```

终端控制台支持：

```
knn <x> <y> [k]          # 近邻查找
range <x1> <y1> <x2> <y2> # 矩形圈选
parcel <x> <y>           # 点-区包含判定
stats                    # 分段与堆占用
```

## 架构

六个核心文件（`src/main/java/com/citygis/spatial/`）：

| 文件 | 职责 |
|---|---|
| `SpatialIndex.java` | 统一门面。管理 KD/R 双索引的构建、原子换代与增量写入 |
| `KDTreeIndex.java` | 点数据 kNN；批量插入与墓碑惰性删除 |
| `RTreeIndex.java` | 矩形范围查询、多边形重叠与点-区包含判定 |
| `SegmentStore.java` | 堆外分段存储（`MappedByteBuffer`，行区 + 批量池两段式布局）|
| `SegmentLoader.java` | 按堆预算切段、段间外排归并；禁止全量载入 |
| `ParallelQueryExecutor.java` | `ForkJoinPool` 并行下发各段查询并归并全局 TopK |
| `IndexWriter.java` | WAL 预写 + 两阶段提交，维护双索引事务一致 |

数据流：数据源 → `SegmentLoader` 分段切分 → 逐段建 KD/R 树并落盘元数据 →
`ParallelQueryExecutor` 并行扫段归并 → `IndexWriter` 经 WAL 两阶段提交。

### 关键设计决策

**行区与批量池分离（`SegmentStore`）。** 段文件分两个区域：定长 40 字节的行区，以及存放多边形顶点的
批量池。若把顶点紧跟在行后，下一行的定长槽位会覆盖它——这正是早期实现中坐标被静默损坏的原因。
分离后两个区域都可用纯算术寻址，追加不会移动既有字节，整段可直接内存映射而无需拷贝到堆。

**行容量一经确定不可更改。** 批量池的基址由行容量推导，放宽映射会平移所有池偏移并损坏存量多边形。
因此 `reopen` 保持 `maxRows` 不变，段在构建时就预留 `EXTRA_ROWS_PER_SEGMENT` 行尾部余量供增量写入追加。

**墓碑惰性删除。** 删除只翻转堆外行标志位（1 字节），不重建树；查询在遍历时跳过。墓碑占比超过阈值时
才由 `compact()` 惰性合并。

**两阶段提交顺序。** WAL 预写并 fsync → 提交阶段一（KD 树）→ 提交阶段二（R 树）。
任一阶段失败按应用顺序逆序回滚（R 树先、KD 树后）。`recover()` 按 **事务** 而非按 WAL 记录做恢复，
避免同一事务被重复计数。

**排序键是全序。** `Neighbor` 按 (距离, id) 排序，因此并行归并的结果与单线程扫描 **逐位相同**，
与分段布局、任务完成顺序无关。属性测试直接断言这一等价性。

**宽窗口自动降级。** 窗口覆盖大部分数据时 R 树剪枝失效，
`rangeSearch` 按分段边界估算覆盖率，超过 `degradeThreshold`（0.5）降级为并行线性扫描。

## 实测性能

在本机（macOS arm64、JDK 24、`-Xmx512m`）实测，非目标承诺：

| 规模 | 分段数 | kNN K=50 耗时 | 构建 |
|---|---|---|---|
| 100 万 | 20 | — | 0.5 s |
| 300 万 | 58 | p50 13ms / p95 28ms / **p99 43ms** | 1.1 s（另计打开 1.1s）|
| 1000 万 | 191 | p50 45ms / p95 64ms / **p99 84ms** | 3.0 s（另计打开 3.2s）|

**与目标 P99 ≤ 50ms 的差距：** 1000 万规模下实测 84ms，未达标。查询扇出到 191 个段文件，
主要成本在每段的存储访问而非树遍历（已将任务按 worker 批处理，从 92ms 降至 84ms）。
进一步优化需要减少段数（如提升单段容量）或改用单文件多段布局，本次未实施。
3 百万规模已满足 P99 ≤ 50ms。

内存：`MemoryBudgetTest` 在真实 `-Xmx512m` 下摄入远超单段预算的语料并断言堆占用不随语料增长。

## 测试

94 项测试，`./mvnw -q test` 全绿：

- **正确性**：kNN、范围查询、包含判定均与暴力扫描（brute force）逐条比对
- **并行等价性**：并行结果 == 单线程结果 == 暴力扫描（`SpatialIndexTest`、jqwik 属性测试）
- **事务一致性**：阶段注入故障验证回滚；混合增删后双索引一致；删除后特征不再复活
- **堆预算**：真实 512MB 上限下摄入与查询的堆占用断言
- **布局不变量**：树连通性（`verifyConnected` 防孤儿槽）、根包络覆盖、批量数据不串行

jqwik 属性测试覆盖：任意坐标/任意 K/任意删除集下 kNN 与全扫描一致；并行合并与分块方式无关；
任意分段布局下范围查询与暴力一致；删除的特征永不复活。

## 已知限制

- 单段容量固定（见上），增量写入超出席部余量时需重建分段
- `rebuild()` 会重建全部分段，停机窗口与语料规模成正比
- 范围圈选返回 `List<GeoFeature>`；10 万级结果集尚无流式接口，堆占用随结果集增长
- 内部 `merge` 采用窗口排序 + k 路归并，段数极大时归并本身的开销需实测评估
