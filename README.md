# obs-ledger — 进程内高吞吐追加写事件账本

面向可观测性场景（审计 + 指标事件）的单进程嵌入式账本引擎。写入侧承接数十个微服务的
并发追加写，读取侧提供按时间窗口回放与参数化过滤查询。**不依赖外部数据库或消息队列**，
所有状态落在本地单文件日志结构存储中。

## 快速开始

```sh
npm install
npm run build

node server.js      # 启动，默认 127.0.0.1:8080
sh verify.sh        # 另开终端执行验收脚本
```

环境变量：`PORT`（默认 8080）、`HOST`（默认 127.0.0.1）、`DATA_DIR`（默认 ./data）、`LOG=0`（静默）。

## 架构

六个文件，单模块，无框架胶水：

| 文件 | 职责 |
| --- | --- |
| `server.ts` | 装配 Fastify、注册路由、生命周期、统一错误兜底。不放业务判断 |
| `store.ts` | 嵌入式存储：追加写日志、LSN 分配、MVCC 快照、后台段合并 |
| `ingest.ts` | 并发摄入：微批合流、背压、按生产者保序、窗口去重 |
| `query.ts` | 查询 DSL 的词法分析 / AST / 参数化绑定 / 注入拦截 |
| `validate.ts` | 请求体与路径参数的 schema 校验 + 消毒器 |
| `errors.ts` | 错误码目录、HTTP 映射、统一响应包装（唯一异常出口） |

数据流：

```
写入  POST /v1/streams/:stream/events
        -> validate 消毒 -> ingest 合流/背压/幂等 -> store 分配 LSN 并落盘 -> 202 {lsn}

读取  POST /v1/streams/:stream/query
        -> validate 消毒 -> query 解析 AST 并绑定参数
        -> store.openSnapshot(lsn) 取一致性快照 -> scanRange 裁剪 -> 谓词过滤 -> 200 {events}
```

## 存储引擎选型（重要）

需求指定 `@sled/native`，但**该包在 npm 上不存在（404）**，而 `sled` 这个包名已被一个
与 KV 无关的同名库（2016 年的滑动条动画库）占用。两者都无法安装。

因此底层换成同属「日志结构 + 单文件落盘」的 **classic-level**（LevelDB 的 Node 绑定）。
上层架构（追加写 / LSN / 快照 / 段合并 / 稀疏索引）完全不受影响，只替换了存储适配器。

键空间布局：

```
EV\0<stream>\0<lsn:16>       -> 二进制事件记录（追加写主日志，LSN 有序）
TI\0<stream>\0<bucket:16>    -> varint(minLsn) varint(maxLsn)（稀疏时间索引）
PS\0<stream>\0<producer>\0<seq:16> -> varint(lsn)（生产者保序 + 幂等）
META\0<head|floor            -> 水位与压缩下界
```

记录用 LEB128 varint 编码字段，比 JSON 省一半以上空间；常驻内存只保留稀疏索引
（条目数与「保留期秒数」成正比，与存量事件数无关）。

## 四个关键设计

### 1. LSN 单调无空洞 + MVCC 快照

LSN 在**批级别**预留（`allocate()`），整个批次共享一个区间。Node 单线程使
「读 nextLsn → 写 nextLsn」天然是临界区，无需锁。

跨批次竞争的处理是关键：LevelDB 的批提交是并发的，提交顺序与 LSN 顺序无关。
若提交后只在 `start <= committedLsn + 1` 时推进水位，那些 start 更靠后但先提交完的批次
将永远等不到前驱，水位卡死、大批已落盘事件对读方不可见（实测 50 并发写只暴露
5220/10000 条）。正确做法是用「已提交区间」的有序结构追踪，每次提交后重算从水位起
**连续覆盖**到的最大 LSN。

读取是两层：LevelDB 快照保证「值不撕裂」，LSN 上界保证「逻辑一致」。写者全程不被阻塞。

### 2. 查询：AST + 参数化绑定

查询串**从不**被拼接进任何底层语句，也从不被当作路径或键名。词法分析切 token，
解析成 AST，字段名对照白名单解析成**列号**，字面量变成**参数槽**。执行时 AST 只携带
`(columnIndex, paramSlot)`，真正的值走 params 数组。

字段名采取**严格拒绝**而非静默折叠：字段名决定读哪一列，放过同形字符会让运维看到的
`sеrvice`（西里尔 е）与真正的 `service` 长得一样却命中不同列，属于误导性越权。
所以字段名必须是纯 ASCII 标识符，任何需要 NFKC 归一化才能命中的写法一律拒。
值则不做此限制——值只以参数参与比较，写入侧已用同一套归一化，两侧一致。

被拦截的变体：分号多语句、`--`/`/* */` 注释、管道与 `&`、点号原型链穿透
（`__proto__`/`constructor`）、引号走私、数字走私（`0x1f`/`1e10`/`1abc`）、
Unicode 同形 / 全角 / 零宽 / RTL 字段名、通配量词炸弹、布尔走私、尾随垃圾 token。
值里的 `; DROP TABLE` 是**数据**，不是语法，因此安全放行。

### 3. 微批合流与幂等

每条事件一次 fsync 会把吞吐压到几百/s，因此按 `(stream, producer)` 分桶合流：
一个流一个待落盘批次，达到阈值或窗口到期就合并成一次 LevelDB batch 提交。
同一生产者的批次严格串行（保序），不同生产者之间并发。

幂等键是 `(stream, producer, seq)` —— 必须按流分域，否则不同流复用同一批 seq 会互相
顶掉（早期版本漏掉 stream，导致第二个流的首次写入被整批判为重复而丢失）。
内存窗口去重挡住窗口内重试，落盘后的持久化幂等键挡住跨窗口重试。

积压超 `maxBacklog` 时以 **rejected promise**（而非同步 throw）返回 429，
调用方的 `.catch()` 才不会漏接。

### 4. 保留压缩与读放大

后台任务按水位合并段、淘汰过期事件、重建稀疏索引。压缩分片进行：每提交一块就让出
事件循环（`setImmediate`），单次压缩的物理删除有总量上限，超出部分留给下一轮。
读方全程走旧段，任何时刻看到的都是「旧段 + 已原子切换的前缀」，不会撕裂。

## 实测性能

`npm run test:perf`（每个用例在独立进程里测，原因见下）：

| 指标 | 要求 | 实测 |
| --- | --- | --- |
| 持续摄入吞吐 | ≥ 20,000 ev/s | **88,440 ev/s** |
| 参数化范围查询 p99 | < 5 ms | **0.289 ms** |
| 写入峰值期快照读 p99 | 不被写者阻塞 | **1.65 ms**（50 并发生产者） |
| 压缩期 p99 恶化 | ≤ 2x 基线 | **1.1x**（实测 6 万条扫描 / 2 万条淘汰） |
| 50 条 keep-alive 连接写入 | — | **78,125 ev/s** |
| 100 万事件常驻内存 | < 512 MB | **160 MB RSS** |
| 100 万事件查询 p99 | < 5 ms | **0.345 ms** |

### 性能测试为什么要独立进程

延迟基准对测量环境极度敏感，这两点是踩过坑之后定下的约定：

1. **必须串行**（`--test-concurrency=1`）。同一份代码与其它测试文件并行时 p99 会被拉到
   30~40ms，串行约 0.3ms。
2. **每个用例独立进程**。LevelDB 后台压缩是异步的：前一个用例写完 5 万条后压缩仍在
   后台跑，这期间测下一个用例，p99 反映的是上一个用例的尾巴（实测从 0.3ms 虚高到 15ms）。

同理，压缩基准的数据时间戳必须相对 `now`：保留期语义是「距今多久」，若样本比 now 早
几个月，压缩会把整段全淘汰——那是「清空整库」的极端情况，不是稳态负载。

## 已知取舍

- 单进程单文件，不做跨机复制；容量受本机磁盘约束。
- 倒序查询（`order: desc`）因 LevelDB 只支持正向区间迭代，实现为「以区间末尾为游标、
  逐段往回退、每段取尾部 N 条」，每轮回退跨度按 4 倍递增。段数多时会比正序多几次
  迭代，但返回的一定是真正的最新 N 条。
- 内存索引随「活跃流数 × 保留期桶数」增长。默认 1 秒一桶、1 小时保留 = 3600 条/流；
  流数量极多时可通过 `timeBucketMs` 调粗。
