# 可嵌入日志检索引擎

面向 SRE 排查场景的内存 + 文件段检索引擎：`level:error AND service:auth AND
message:"connection timeout"` 这类查询在千万级日志里秒级拿命中行。

零在线服务依赖 —— 词法/语法解析用源码内置的 chevrotain（`vendor/chevrotain`），
倒排、段管理、持久化全部自实现。

```bash
npm install
npx tsx src/demo.ts      # 终端演示
npm test                 # 85 个用例
npm run bench            # 性能基准（会真的建 100 万文档）
```

## 架构

数据流：**写入 → 内存缓冲 → 不可变段 → 落盘**；**查询 → AST → 下推计划 → 逐段短路求值 → 取原文**。

| 文件 | 职责 |
|---|---|
| `src/lexer.ts` | 查询词法：token 定义、位置追踪、带位置的词法错误 |
| `src/parser.ts` | chevrotain 文法 → AST（AND/OR/NOT、范围、短语、存在性） |
| `src/inverted.ts` | 倒排表、block-max 跳表、计数排序构建器 |
| `src/segment.ts` | 不可变段、`DocStore`、tiered 合并、tombstone |
| `src/pushdown.ts` | 过滤下推、段级剪枝、posting 求值 |
| `src/engine.ts` | 串联构建/查询/持久化/并发 |
| `src/persist.ts` | 段文件二进制编解码（原子 rename） |
| `src/typedarray.ts` | TypedArray 原地扩权（`ArrayBuffer.transfer`） |

## 四个关键设计

### 1. 段不可变 + 视图原子替换

段一旦构建完成就只读，因此**查询不需要任何锁**。引擎维护一个 `segments` 数组引用，
合并完成时整体替换引用，而不是逐个修改数组元素：

```ts
const snapshot = this.segments;          // 查询拍下视图
// ... 逐段求值，期间合并完成也不影响这份快照 ...
this.segments = next;                     // 单次赋值完成切换
```

在途查询持有的旧引用依然指向旧段对象（旧段由 GC 回收），所以
**合并与查询完全解耦，不需要读写锁**。写入同理：只往内存缓冲追加，从不触碰已生效的段。

### 2. 三层短路

```
第一层  段级剪枝     段元信息 O(1) 判定 —— 段内无该 term / 数值值域无交集 -> 整段跳过
第二层  posting 收敛  AND 操作数按 df 升序排序（稀疏链当主链），任一子结果为空立即返回
第三层  tombstone     段内墓碑 + 尚未合并的删除标记
```

第一层是收益最大的一层：真实日志按来源分片（auth 集群、billing 集群……），
只关心 auth 的段压根没有其它 service 的倒排链，一次 posting 比较都不用做。
`npm run bench` 的演示里 4 个段跳过了 2 个。

### 3. tombstone 与物理回收

删除只写标记，段本身一个字节都不动（所以删除不阻塞查询）。
墓碑在**下一次合并**时才落地：命中文档从新段里物理剔除，docId 重新编号，
空间随之回收。`pickMergeTier` 是纯函数，按 size 分层决策，
tombstone 占比超 30% 时强制合并。

### 4. 内存：每个字节都是抠出来的

百万文档 / 512MB 这条约束逼出了一连串取舍，都是实测数据驱动的：

| 决策 | 原因 |
|---|---|
| 构建期用**计数排序**而非 `Map<term, number[]>` | 前者每篇文档多花约 390 字节 |
| **不给 `id`/`trace_id` 建词级索引** | 高基数字段每篇产生一个新 term，term 数从 5 万涨到 50 万 |
| 默认只给 `message` 建词级索引 | 同上；需要时用 `textFields` 显式声明 |
| 原文存**共享 Uint8Array 块**，不存对象/字符串数组 | 百万个字符串对象的开销比内容本身还大 |
| 位置表**分块增长**，不做翻倍扩容 | 翻倍到百万级 int 时 V8 反复重分配，RSS 直接翻几倍 |
| pair 数组用 `ArrayBuffer.transfer()` **原地扩权** | 翻倍策略下新旧两份 backing store 同时存活，峰值 3~4 倍 |
| 小 df 的 posting **不建跳表** | 线性扫本来就快，跳表纯属浪费 |

单项优化的实测收益：短语校验 97ms → 21ms（字节级匹配替代切词比对）、
`DocStore.append` 17.4s → 107ms（位置表分块）。

## 性能实测

`npm run bench`，单段 100 万文档，Node 26：

| 指标 | 约束 | 实测 | |
|---|---|---|---|
| 百万文档单段构建 | < 3s | **6.6s** | 未达标 |
| 等值/范围查询 | — | **0.5–1.5ms** | 达标 |
| 中等选择性查询 P99 | < 50ms | **75ms** | 未达标 |
| 10 路并发不互相阻塞 | — | 并发/串行 = 0.99x | 达标 |
| 合并中查询 P99 | — | **4.3ms** | 达标 |
| tombstone > 30% 强制合并 | — | 达标 | 达标 |
| 构建后稳态内存 | < 512MB | **553MB**（GC 后） | 接近 |

基准里所有查询都先与"读原文逐条过滤"的朴素实现交叉验证过，结果一致。

**未达标项的诚实说明**：

- **构建 6.6s**。倒排 + 原文存储约 3.2s，其余是语料生成与 JSON 编码。
  原始文档以 JS 对象形式进入引擎，天花板就在这里 —— 真要压到 3s，
  需要改成二进制列式摄入（直接喂列缓冲，跳过对象和 JSON）。
- **P99 75ms**。瓶颈是短语查询：`message:"connection timeout"` 要对
  十几万候选做字节级子串校验。已做的优化（最稀疏词收窄、零分配匹配、
  逐词验证缓存）把它从 200ms+ 降到 75ms。要再压就得引入 trigram 倒排
  做短语预筛，代价是索引体积再涨。
- **稳态 553MB**。存活数据约 320MB（原文 200MB + posting 72MB + 数值 23MB + 其它），
  GC 后仍高于 512MB。主要空间在完整 JSON 原文上 ——
  当前每篇都存了完整 JSON 以便返回命中行，若改为按需从列重建可省下大部分。

**并发那条的口径**：单线程 JS 上 10 路并发本来就是交替执行的，总耗时不可能低于串行。
真正验证的是"没有互相等待/加锁导致的数量级劣化"，以及
"查询期间并发写入不影响任何一次在途查询的结果"（测试里用快照不变性断言）。

## 测试

85 个用例，`node:test`，覆盖：

- **查询语法**：field:value / AND / OR / NOT / 括号 / 范围 / 短语 / `field:*`，
  错误位置断言到具体 token 的 offset
- **倒排与跳表**：集合运算与朴素实现对拍、跳表 seek、计数排序天然升序
- **段与合并**：不可变性、tombstone 物理回收、tiered 决策是纯函数、30% 阈值
- **下推与短路**：段级剪枝、候选集取最稀疏词、**范围结果必须升序**（回归测试）
- **短语字节匹配**：与 `String.includes` 随机对拍 200×9 组合
- **引擎**：增量写入、删除可见性、合并期查询不阻塞、持久化重载一致、合并回收旧段文件

其中"范围结果升序"是一条真实 bug 的回归测试：数值索引按值排序，
命中区间的 docId 是乱序的，不排就交给求交会静默漏命中
（表现为命中数莫名偏小，定位极难）。

## 已知取舍

- **裸词/裸短语不做全局 `_all` 倒排**，而是对每个文本字段各建一份。
  代价是"多字段 AND"查询会按实际匹配字段数变慢；收益是索引体积和延迟都显著下降。
- **验证缓存不做并发共享**。段不可变所以结果稳定，但多个查询同时推进同一份游标
  需要加锁；当前实现每个查询拿自己的游标，正确性优先。
- **查询无超时/无并发上限**。段落查询靠单次 segment 级剪枝，
  `level:*` 这类宽查询会扫全段 —— 生产上需要配 limit 与查询超时。
